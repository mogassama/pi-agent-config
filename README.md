# Pi config — data engineering setup

Personal `~/.pi/agent/` configuration for data engineering work (Python, SQL, GCP).

Delegation is handled by a local extension written for this setup, not by a
third-party one. Everything below is measured; where a number appears, it came
from a run, not from a guess.

## How the pieces fit

Pi ships seven built-in tools (`read`, `write`, `edit`, `bash`, `grep`, `find`,
`ls`) and **no delegation primitive of its own**. `~/.pi/agent/agents/` is a
convention two extensions invented independently; the core knows nothing about
it. Delegation here is `extensions/subagent/`.

| Layer | What it is | Cost | When to use |
|---|---|---|---|
| **AGENTS.md** | Always-loaded global rules | ~4 200 tokens, every session | True for every session |
| **APPEND_SYSTEM.md** | Appended to pi's system prompt | Every session, orchestrator only | Behavioural defaults, terse framing |
| **Skills** | Description in the prompt, body on demand | ~145 tokens each until loaded | Domain rules |
| **Prompt templates** | Manual via `/<name>` | 0 until invoked | Repeatable workflows |
| **Subagents** | A fresh `pi` process per call | ~1 500–6 000 tokens, separate budget | Search, isolation, a different model |

Orchestrator context at startup: **8 803 tokens** (print mode).

## Delegation

One tool:

```text
task({
  agent,
  task?,
  skills?,
  find?,
  scope?,
  for_risks?,
  work_unit?,
  batch?,
})
```

`find` and `scope` are the scout's input contract; a scout call without them is
refused before anything is spawned. `batch` is worker-only and mutually
exclusive with `task`: each item names its own `work_unit` and instruction.
Each child is a fresh `pi` process with its own model, tool allowlist, hooks and
skill slices.

**A child inherits nothing.** No AGENTS.md, no conversation history, no prior
tool calls, no `.pi/BRIEF.md`, no `APPEND_SYSTEM.md`. What is not in the task
text or injected by the extension does not exist for it.

That is a deliberate reversal. The previous setup forked the parent session into
each child: 17 041 tokens, of which 2 were fresh — almost all cache reads, so
the cost argument against it never held. What condemned it was control, and a
measured failure mode: a fork carries the parent's text but not its tool calls,
so a reviewer once accused the orchestrator of fabricating its own delegations.

### Agents

| Agent | Model | Fallback | Thinking | Tools | Turns |
|---|---|---|---|---|--:|
| `worker` | `openai-codex/gpt-5.6-terra` (subscription) | `gpt-5.6-sol` | high | read, grep, find, ls, bash, edit, write | 30 |
| `integration-worker` | `openai-codex/gpt-5.6-terra` (subscription) | `gpt-5.6-sol` | high | read, grep, find, ls, bash, edit, write | 30 |
| `reviewer` | `anthropic/claude-sonnet-5` (API) | `gemini-3.1-pro-preview` | medium | read, ls | 12 |
| `scout` | `deepseek/deepseek-v4-flash` | `gemini-3.1-flash-lite`, `gemini-3.5-flash-lite` | low | read, grep, find, ls | 12 |
| `advisor` | `xai/grok-4.6` | `gemini-3.1-pro-preview` | xhigh | read, grep, find, ls | 8 |

Every role runs ephemeral. `--session-id` is passed either way, so provider cache
affinity does not depend on carrying history — and history, measured, was carried
and not used: 24 re-reads of byte-identical content already in the session.

Four model families, deliberately separated across worker, reviewer, scout and
advisor. `integration-worker` shares the worker family because it is another
producer; the independent reviewer remains on a different family. A reviewer
on either producer's family is a judge-and-party arrangement and
`/check-config` blocks on it. The fallback chains do **not** currently respect
the same rule: reviewer and advisor both fall back onto
`gemini-3.1-pro-preview`, so a day on which both primaries fail would put judge
and second opinion on one model. `/check-config` reports it rather than blocking
— it is a trade-off to take knowingly, not a discovery to make during an
incident.

Scouts run in parallel when several are asked at once: `find` takes an array, up
to four, and each child answers one question against the same scope. Nothing is
merged — the subtraction between two answers stays with the orchestrator. Writers
are excluded from this by construction, not by a setting: a scout cannot change
the tree, so nothing the configuration says about state can go stale underneath
it.

The reviewer has neither `bash` nor `grep`: it judges files, the scout finds them,
the orchestrator decides which. It is handed the diff instead — built by the
extension from everything written since the last review, since workers never
commit and `HEAD~1` fails on a single-commit bundle repo. Above 15 files or 80 kB
of diff the task carries the file list instead, and the reviewer gets `grep` and
`find` back for that delegation: the tools follow the input package, not the
role.

`advisor` is **in service since 24 August 2026 and has never yet been invoked**:
its five conditions are cumulative, and on a bundle project they rarely all hold
at once. A role that fires on nothing is telling you the regime does not produce
its situation. It points at
`grok-4.6` at `xhigh` with Gemini Pro behind. The reviewer stayed on Sonnet 5
after two measured gates — Gemini 3.7 Flash missed a quadratic defect entirely,
DeepSeek V4 Pro returned one finding across eleven reviews where Sonnet returned
fourteen across seventeen. Cheaper judges were measured and refused.

Definitions live in `subagent-only/agents/*.md` — frontmatter for the wiring,
body for the role prompt. Every failure is raised at load time, not mid-task: a
missing `submit` tool, an inconsistent `sliceMode`, an unknown skill, a provider
with no package.

### Work units, lanes and integration

A **WorkUnit** is a logical, independently reviewable change. A **Lane** is its
physical execution context: one Git worktree and branch. They are deliberately
different objects; rework stays on the same WorkUnit and returns to the same
lane.

Before the first code-producing delegation, the orchestrator writes
`.pi-subagent-runs/<run>-plan.json` with each unit's dependencies and expected
write scope. The runtime attaches its hash to the manifest and does not rewrite
the plan after seeing the work: it is a prediction used to measure the quality
of decomposition, not a history edited after the fact.

Worker batches run at most two lanes concurrently by default. Override that
only explicitly:

```bash
PI_SUBAGENT_MAX_PARALLEL_LANES=2 pi
```

The scheduler admits only known units whose dependencies are integrated. It
keeps scope ownership after a worker returns and until the unit is integrated;
an overlapping unit waits instead of opening a competing worktree. Invalid
values such as `0`, `-1` or a fraction fail rather than silently falling back to
serial execution.

Children never own Git mutations. Workers edit their lane; the root runtime
reviews the resulting tree, integrates it, and records the durable fact. A
mechanical merge conflict is resolved in a throwaway integration worktree by
`integration-worker`, limited to the conflicted files. That resolution is
reviewed before the runtime creates the merge commit. The committed tree, the
reviewed tree and the landed commit are checked as the same object.

### Durable run and recovery

The run survives the orchestrator session. Its manifest, frozen plan, lane
events and IntegrationAttempt events live under `.pi-subagent-runs/`; lane
worktrees and branches plus `.git/pi-integrations/` are the physical state.
Every durable mutation requires the run lease. A second session may inspect the
run but cannot reserve a sequence, open a lane or write an event.

At startup, runtime state is reconstructed by reconciling the ledgers with Git.
The runtime and the operator tool use the same `observeLanes` and
`observeIntegrations` snapshots, including one shared read of the lane ledger.
An unknown ledger version or malformed line is fail-closed: no partial state is
published and no destructive cleanup plan is derived from the readable prefix.

Operator commands are explicit; none infers a missing business fact:

```bash
bin/subagent-recover                         # contradictions and allowed actions
bin/subagent-recover attempts                # IntegrationAttempts and phases
bin/subagent-recover <unit> adopt
bin/subagent-recover <unit> integrated
bin/subagent-recover <unit> abandoned
bin/subagent-recover <unit> discard
bin/subagent-recover attempt <id> return-to-lane
bin/subagent-recover attempt <id> discard-context
bin/subagent-recover cleanup                 # dry-run; shows removed and retained
bin/subagent-recover cleanup --apply         # recomputes the plan under the lease
bin/subagent-recover report
bin/subagent-recover report --json
```

Inside Pi, `/subagent-report` renders the same terminal report. Reporting is a
pure projection of the two observer snapshots and the cleanup plan; it performs
no Git probe of its own. The report includes WorkUnit states, surviving physical
objects, cleanable and retained objects with reasons, recovery conflicts and
warnings, `recovery_scan_ms`, `git_probe_count` and the run-branch count. A
missing or unreadable IntegrationAttempt ledger is represented as unknown
(`null` in JSON), never as an empty list.

`cleanup` never writes lane or integration events. It removes only objects
already certified as cleanable by reconciliation, with worktree before branch;
if removing the worktree fails, its branch is retained. The transverse rule is:
after every deletion, an authoritative proof or reference still names any
content the deleted object could have carried.

### Searching is scout work

Reading one file you can name is inline. **Searching across files is a
delegation.** The moment the question is *where* rather than *what*, it goes to
the scout, on a model costing a fraction of the orchestrator's.

The tell is the tool you are reaching for: a `read` on a named path is yours, a
`grep` across the tree is the scout's.

### The output contract is a tool, not an instruction

Each child loads a micro-extension registering `submit`, whose parameters **are**
that role's schema, with `terminate: true`. Validation is TypeBox on tool
arguments, done by pi, before anything is written.

This replaced a contract stated in prose. Measured on ten reviewer runs of the
old setup: the envelope appeared 5/5 when the task text named it and 0/3 when it
only described the work. A loaded skill never imposes its own output format, so
the closing instruction is appended by code, not left to whoever writes the task.

The schema is flat — each child sees one role, so a `payload` wrapper separated
nothing and cost a failed validation plus a retry on three runs out of three.
`dispatch` rebuilds the envelope/payload split when it writes the artefact.

### Reading a result

The tool returns one line plus an artefact path. Returning the whole payload
would rebuild, one delegation at a time, the context bloat this exists to
remove. The full envelope is in `.pi-subagent-runs/` (gitignored), with the
child's raw stream beside it.

```bash
bin/subagent-trace              # the most recent run
bin/subagent-trace --all        # one line per run
```

Turns, calls per turn, tools used, bash commands, context growth, token split.
Only totals crossed back before, and a total cannot tell a role that **reads**
its way to an answer from one that **searches** its way there. Calibrating the
scout with it took its context peak from 42.6k to 9.1k and its cache reads from
102k to 8k.

### Skill slices

A domain skill ends with `## Review delta` — the section a reviewer receives on
top of the authoring guidance, holding that domain's severity table.

| Role | Injected |
|---|---|
| `worker` | everything above the marker |
| `reviewer` | the whole body |
| `scout`, `advisor` | nothing by default |

Bodies are injected as text through `--append-system-prompt`, never `--skill`:
`--skill` injects name, description and path only, so the child would spend a
`read` turn opening what we already have.

`.pi/BRIEF.md` is injected before any skill for roles that declare
`projectBrief: true` — no role today. AGENTS.md forbids assuming
project layout, and without the brief a worker obeys by spending turns
discovering it; a turn costs a full context re-read, so one avoided turn repays
the ~400 tokens. The scout finds structure by searching, and a brief would point
it at what the brief happens to mention. The reviewer judges against a severity
table, and project specifics belong in the task text.

**Which domain applies belongs to the task, not the role.** Agent definitions
declare no domain default — a default right one time in three is worse than
none, and it invites the orchestrator to omit the parameter. Pass it per call:
`task({ agent: "reviewer", skills: ["iac-terraform"], task: "..." })`.

The `## Review delta` marker is guarded by `/check-config`, not at runtime:
failing there is free, whereas a delegation aborted over a skill that
legitimately has no delta costs a whole run.

## Tests

```bash
bin/test-guards                    # complete suite, no install step
bin/test-guards guards             # one ordinary Node test file
bin/test-guards execute-harness    # one harness, with the Pi/TypeBox loader
```

The frozen `3c` candidate was independently replayed on a fresh clone from
`2499ea9` and passed three consecutive full runs:

```text
762 ordinary Node tests
91 loader-backed harness tests
65 Python tests
```

The ordinary tests use `node --test` with type stripping. Harness files run in
a separate Node process with explicit Pi and TypeBox substitutes; Python checks
the shadow-run reader. Naming `*-harness.test.ts` is the executable convention:
the runner discovers every such file instead of keeping a hand-written list.

Coverage includes:

- shell and credential guards, extension/skill/role consistency;
- WorkUnit validation, dependency admission and scope ownership;
- real concurrent workers in distinct Git worktrees;
- durable manifest/lease/sequence and both append-only ledgers;
- IntegrationAttempt crash boundaries and reviewed-tree/commit/landed identity;
- fail-closed observation, recovery actions and cleanup safety;
- deterministic terminal reports and exact Git-invocation accounting;
- installation artefact containment and Git hook enforcement.

The predicates live in `subagent-only/role-rules.ts` and
`extensions/pi-secret-gate/rules.ts` — leaf modules importing nothing from pi,
split out for exactly this reason. The extension files are the wiring.

What the suite cannot establish is whether a model honours a prompt, or whether
parallel execution is reliable over a full production task. The first is
measured by delegations. The second remains deliberately unclaimed until the
first Balance Âgée run with `maxParallel=2`.

There is no green repository-wide `tsc --strict` gate yet. The known local
baseline is 120 strict errors, all predating `3c.2c.3b`; that lot added none and
removed four by typing `registerCommand` in the Pi stub. The local strict config
contains machine-specific paths, so the number is recorded debt, not presented
as a reproducible CI guarantee.

The case that produced `config.test.ts`: `pi-secret-gate` was declared in
`worker.md` and never committed. It existed on one machine, so every local run
worked and every clone failed at `resolveExtension` before a child spawned.
Nothing in the repository could notice.

Git hooks are not Pi extensions. `commit-msg` enforces Conventional Commits at
the Git level. `pre-commit` refuses a commit from any process carrying
`PI_SUBAGENT_ROLE`, and `reference-transaction` refuses child-owned ref moves.
The latter two are defence in depth: working-tree and index mutations that do
not move a ref remain the responsibility of `role-guard`. Hooks are not
installed automatically because replacing a repository's hook path is an
operator decision.

Three categories, and `/check-config` enforces that every skill is in exactly one:

- **Reviewer-facing (11)** — carry a `## Review delta`. A missing marker is
  blocking: a reviewer handed the file without its severity table would invent
  one.
- **Mechanism (1)** — `code-review`, injected whole through an agent's
  `mechanism` field. It holds the severity definitions, the confidence axis and
  the verdict rule, and no domain content: the five domain blocks it used to
  carry now live in the domains they belong to.
- **Orchestrator-only (7)** — `git-collaboration`, `grill-me`, `diagnose`,
  `improve-codebase-architecture`, `dataeng-architecture`,
  `gcp-dataeng-architecture`, `tdd`. Invoked with `/skill:<name>`, never injected.

Do not remove concrete examples merely to reduce line count. A schema reduced to
a pointer was not followed in measured runs; the same schema shown as a JSON
block was.

> **One rule, one file. One severity per surface where the rule can be
> breached.** "Never blind `WRITE_APPEND`" is stated once, in
> `bigquery-engineering`; its weight exists in `python-engineering` and
> `airflow-engineering` too, because a reviewer loads only the skill matching
> the file under review. A severity duplicated across surfaces is fine. A
> severity that **contradicts** itself across surfaces is not.

## Daily usage

```bash
pi                                          # interactive, all global config
pi "review @dags/billing_dag.py"           # interactive with initial prompt
pi -c                                       # continue last session here
pi -r                                       # browse and resume sessions
pi -p "..."                                 # one-shot, prints and exits
pi --model sonnet:high "..."               # override model + thinking level
pi --tools read,grep,find,ls "..."         # read-only
```

In-session: `/skill:<name>` force-loads a skill, `/<template>` expands a
template, `/reload` picks up config changes, `/compact` summarises older
context, `/check-config` runs the consistency check, `/footer` toggles the
footer, `/tree` branches off a prior message. `shift+tab` cycles the thinking
level — it shows in the footer.

Measuring the initial context, which is the instrument every decision here rests
on:

```bash
cd ~/bench-pi-baseline
pi --mode json -p --no-session "hi" 2>/dev/null | python3 -c "
import sys,json
for l in sys.stdin:
    try: e=json.loads(l)
    except: continue
    m=e.get('message') or {}
    if e.get('type')=='turn_end' and m.get('role')=='assistant':
        print(m.get('usage',{}).get('input')); break"
```

## Adding a skill

```bash
mkdir -p ~/.pi/agent/skills/<name>
cat > ~/.pi/agent/skills/<name>/SKILL.md <<'EOF'
---
name: <name>
description: One precise sentence on when to auto-load this skill. Vague descriptions trigger badly. Max 1024 chars.
---

# <Name>

## When this skill is active
...

## Rules
...

## Anti-patterns — never do these
...

## Review delta
*Reviewer-facing skills only. Severity table, not a restatement of the rules.*
EOF
```

Then `/reload`, and `/check-config` to confirm the classification.

- `name`: lowercase, a-z, digits and hyphens, ≤64 chars, matching the directory
- `description`: the only field pi uses for auto-loading — make it specific
- Add it to `reviewerFacingSkills`, `mechanismSkills` or `orchestratorOnlySkills`
  under `settings.json` → `checkConfig`, or `/check-config` will report it as
  unclassified

## Adding an agent

Create `subagent-only/agents/<name>.md`, and add the role to the union in
`envelope/envelope.ts` with its payload schema. `/check-config` blocks on a
definition with no schema, and reports a schema with no definition.

## Maintenance

```bash
/check-config                    # blocking and report tiers
bin/subagent-trace --all         # every delegation this project has run
pi --no-session "test"           # verify no extension fails to load
```

**When to update a skill:** when the agent does something wrong that a rule
would have prevented. Append to `## Anti-patterns`, and weigh it in
`## Review delta` if the skill is reviewer-facing. No speculative rules.

**When to add a prompt:** when you have typed the same setup more than three
times in a session.

**When to reconsider a role:** when `bin/subagent-trace` shows it reading more
than it searches, or hitting its turn ceiling. Both are visible; neither is a
judgement call.
